END-SESSION
===========
Starts on: "end the session", "wrap up", "we're done for today".
Leaves:    a building, committed tree; a session log saying where to pick up;
           nothing of ours still running; a short summary in chat.

Work the steps in order. If a step fails, fix it or say plainly that it is
being left broken and why - never skip it silently.

STEPS
1. Stop what this session started.
   Close any game window or background cargo run by the process ID recorded
   when it was launched. Never by name or pattern (CLAUDE.md rule 3). If
   something is running that this session did not start, leave it and tell
   the owner.

2. Build green.
       cargo check
       cargo test
   Read the real exit codes (build-and-run.txt). If anything visible changed
   this session and has not been looked at, take one screenshot run now and
   read the image. Warnings introduced this session are fixed, not left.

3. Code commit.
   git status, then git diff - read what is actually going in. Commit code and
   data together with a message saying what changed and why. Nothing from
   /target, /screenshots or *.log belongs in it; if one shows up, fix
   .gitignore rather than adding it. If the tree does not build and cannot be
   fixed now, commit it on a branch named wip-<slug>, not on the main branch.

4. Bring the written record up to date - only what this session made untrue.
   - docs/<system>.txt for any system built or changed (how it works now).
   - procedures/: a routine done for the second time gets its file and its
     INDEX.txt line; a procedure that misled this session gets corrected.
   - CLAUDE.md: only if a standing rule, the pinned Bevy version or the layout
     changed. It is not a log.
   - Memory: save what the owner corrected or asked for as a standing thing;
     delete any memory that is no longer true.
   - GitHub issues: every question raised this session and left unanswered
     is in an issue labelled "decision" (owner, 2026-10-09). A question that
     was only said in chat is lost; file it before the log is written.

5. Write the session log: a NEW file
       docs/session-log/<YYYY-MM-DD>-<HHMM>-<slug>.txt
   Never append to an older one. Keep it short, with these headings:
       ASKED       what the owner asked for, in her words where possible
       DONE        what was built, each with how it was checked
                   (compiled / tested / seen running / owner looked)
       DECIDED     design calls she made, and any made for her - say which
       FOUND       bugs, API quirks, surprises
       NOT DONE    what was started and left, what was never run or looked at
       PICK UP     the first thing the next session should do
       NEXT RELEASE  what is left until the next release (see below)
   The next session reads PICK UP before anything else, so make it one
   concrete action, not a list of themes.

6. Docs commit. Commit steps 4 and 5 separately from the code.
   Then push to origin (github.com/9-7-8/horse-heroes, public since
   2026-10-09) and say so. The repo is public: read the session log once
   more for anything private before it goes up.

7. Verify clean. git status shows nothing to commit; no process this session
   launched is still alive.

8. Summarise in chat, result first, a few lines: what works now, what is
   unverified, what to pick up. The detail is already in the log.
   Then the log's NEXT RELEASE block, as it is there.
   End the summary with the words "safe to clear" (owner, 2026-10-10), and
   only once steps 1 to 7 are really done: pushed, clean, nothing running.
   If any of them is not, say what is outstanding instead.

NEXT RELEASE (step 5; owner, 2026-10-14: "display what's left until the
next release"). Counted after the issues are closed and filed, so it is
true when the log is pushed. The next release is the first release
milestone, in version order, after the latest published release:
       gh release list --repo 9-7-8/horse-heroes --limit 1
       gh api "repos/9-7-8/horse-heroes/milestones?state=open&per_page=100" --jq '.[] | "\(.title)\t\(.open_issues) open\t\(.closed_issues) closed"'
       gh issue list --repo 9-7-8/horse-heroes --milestone "<x.y.z Theme>" --state open
   Say it as a short block: the release's name and how many of its issues
   are closed of how many, then EVERY issue of the release, closed ones
   too, one line each, as "#N title - status". The status is always one of
   three words, no others (owner, 2026-10-15: "unbuilt / built-untested /
   closed"):
       closed          the issue is closed.
       built-untested  open and labelled "built": everything is built and
                       committed and it waits only on her trying it. Put
                       the label on when an issue is left open for that
                       alone, and say so in a comment on it.
       unbuilt         any other open issue, whether nothing of it is
                       built, part of it is, or it waits on her ruling
                       (decision, proposed).
       gh issue list --repo 9-7-8/horse-heroes --milestone "<x.y.z Theme>" --state all --json number,title,state,labels
   Example:
       0.2.4 Fixes from testing 0.2.3: 1 of 10 closed.
         #354 Each horse attacks at its own cadence - unbuilt
         #356 Select a horse by pressing it in the scene - built-untested
         #360 A lesson pop-up when the boss is met - closed
   Under it, any
   issue labelled "menus" from another milestone that was finished or
   built in part since the latest release: it rides this one (menus
   first) and is listed as riding along.
       gh issue list --repo 9-7-8/horse-heroes --label menus --state closed --search "closed:><date of the latest release>"
   A menus issue still open that this session built part of is listed as
   riding along in part.

DO NOT
  - End on a red build without saying so in both the log and the summary.
  - Write "works" for something that was only compiled.
  - Tidy, refactor or start anything new during this routine.
  - Ask the owner anything in prose at the end; a real question goes through
    the question tool before the summary.
